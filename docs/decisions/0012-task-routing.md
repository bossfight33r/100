# ADR-0012: Маршрутизация задач по тегам воркеров

**Решение.** `compute/routing.py`. Задача несёт `TaskRequirements.tags` (из `CF_JOB_REQUIRE_TAGS`) и ставится в RQ-очередь `clipfactory@<теги через +>`. Воркер вычисляет функциональные теги из `WorkerCapabilities` (`gpu` — h264_nvenc прошёл пробное кодирование, `mac` — videotoolbox, `mlx` — mlx-whisper) плюс `CF_WORKER_TAGS`, и слушает очереди всех подмножеств своих тегов (специфичные первыми) и базовую. Heartbeat в Redis (`cf:worker:<имя>`, TTL 60 с) — по нему `enqueue` предупреждает, если подходящего живого воркера нет.

**Почему.** Pipeline описывает требования, а не машину (раздел 5 ТЗ); перенос рендера на GPU-сервер — это `CF_JOB_REQUIRE_TAGS=gpu` на клиенте и воркер с NVENC, без изменения этапов.

**Сохранение требований.** Теги требований пишутся в `jobs.require_tags` при создании job (миграция v3): восстанавливающий воркер ставит job в её исходную очередь, а не по своим настройкам. Реестр живых воркеров — Redis SET `cf:workers` + ключи heartbeat с TTL (без SCAN).

**Ограничения.** Маршрутизируется job целиком, а не отдельные этапы; для разных машин нужно общее хранилище (`CF_STORAGE=s3`) и общая БД.

**Отброшено.** Отдельный брокер/планировщик (Celery, Nomad) — избыточно для одного владельца; маршрутизация по `platform.system()`.
